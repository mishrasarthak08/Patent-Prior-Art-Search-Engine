# Technical Audit & Target Architecture Specification
**Platform**: Patent Prior-Art Intelligence & Claim Analysis Engine
**Audit Date**: November 2026
**Lead Architecture Team**: Antigravity Principal Engineering & Product Leadership

---

## 1. Executive Summary & Existing System Audit

A thorough, code-level inspection of the repository was conducted across backend services, retrieval pipelines, AI models, data storage, evaluation harnesses, frontend UI, security, and deployment manifests.

### 1.1 Existing Architecture Summary
- **Backend**: FastAPI web server with a LangGraph state machine orchestrating claim decomposition (Gemini Flash), BM25 (local pickle file), dense retrieval (Gemini Embedding 2 + Qdrant), reciprocal rank fusion (RRF), cross-encoder reranking (Cohere v3), and explanation generation (Gemini Flash).
- **Frontend**: Single-page Next.js 16 / React 19 interface (`page.tsx`) submitting claims to `/search` and displaying basic cards with hardcoded UI elements.
- **Corpus & Storage**: Local pickle file (`bm25_index.pkl`) and 3-document test parquet (`corpus.parquet`). No relational or persistent database.

---

## 2. Critical Findings & Architectural Deficiencies

| Subsystem | Existing State | Critical Flaw & Risk | Target Redesign |
|---|---|---|---|
| **Persistence & State** | Completely stateless in-memory requests. No database. | Searches vanish on page reload. No project workspaces, no saved prior-art candidates, no persistent claim charts, no audit trails. | Relational database (SQLite/SQLAlchemy) storing Projects, Searches, Documents, Evidence Mappings, Annotations, and Benchmark Runs. |
| **Claim Understanding** | Freeform LLM prompt to Pydantic parser. | No character offset tracking; cannot trace extracted limitation back to exact span in original claim. If decomposition fails, silently falls back and disables dense retrieval entirely. | Traceable claim decomposition with exact char spans (`start_char`, `end_char`), preamble/transition extraction, entity/term extraction, and structured validation. |
| **Lexical Retrieval** | BM25Okapi using Python pickle (`bm25_index.pkl`). | Pickle files pose security risks and cannot scale or query dynamically. Filters (`cpc`, `date`, `jurisdiction`) are in signature but completely ignored. | Production-grade lexical engine with field weighting (Title, Abstract, Claims, Description), dynamic CPC/Date/Jurisdiction filtering, and SQLite FTS5/BM25 backing. |
| **Dense Vector Retrieval** | Qdrant vector search using Gemini Embedding 2 (3072d). | Metadata payload in Qdrant lacks document title and full passages. CPC/Date filters declared in code but never passed to Qdrant filter DSL. | Full-payload vector indexing with CPC/Date filter DSL, versioned collections, and element-level parallel search. |
| **Cross-Encoder Reranking** | Cohere Rerank v3. | **Critical Defect**: Only reranks against `snippet` truncated to 250 characters (`text[:250] + "..."`), throwing away 90% of technical disclosure. | Passage-aware window reranking against full relevant claim/abstract/passage disclosures, with local cross-encoder fallback. |
| **Evidence & Explainability** | Single unstructured text paragraph generated by LLM from 250-char snippet. | No evidence verification: LLM can hallucinate disclosures with zero grounding. No limitation-by-limitation claim chart. | Evidence-first claim chart engine: limitation-by-limitation mapping with automated substring quotation verification against actual patent text. |
| **Document Deduplication** | Only dedupes by exact publication ID string. | Multiple publications of the same patent family (US, EP, WO) clutter search results. | Patent family resolution with configurable family-level deduplication. |
| **Data Ingestion** | `pull_corpus.py` queries BigQuery; `build_dense_index.py` deletes collection on every run. | No reproducible multi-domain benchmark corpus. Test parquet has only 3 documents. | Reproducible multi-domain patent corpus (Batteries, AI/Computing, Semiconductors, Comms, MedTech) with full claims, descriptions, and citations. |
| **Evaluation System** | Static CSV file `lift_table.csv` read by API endpoint. | Benchmark results are hardcoded. `run_eval.py` looked for non-existent `eval/gold_set.json`. | Versioned benchmark datasets, automated ablation suite (BM25, Dense, Hybrid, Rerank, Full), and dynamic evaluation reporting. |
| **Security & Privacy** | Static default API key `dev_key`, wildcard CORS `*`. | Confidential invention disclosures submitted by users are logged in plain text and transmitted over unauthenticated endpoints. | Secure API authentication, origin controls, and Confidential Mode hashing/masking sensitive invention claims in logs. |
| **Frontend UI** | Single 415-line component with hardcoded steps and mock numbers. | No workspace management, no claim chart matrix, no full document viewer, no search history, no export reporting. | Professional multi-view enterprise workspace: Claim Investigator, Claim Chart Matrix, Full Patent Document Viewer, History, and Export Dossier. |

## 4. Implementation Roadmap
- **Phase 1**: Foundational Data Models, Settings, and Relational Persistence (`backend/app/db/`).
- **Phase 2**: Multi-Domain Ingestion & Comprehensive Patent Corpus with Full Text & Families.
- **Phase 3**: Enhanced Claim Decomposition with Character Spans & Multi-Limitation Hybrid Retrieval.
- **Phase 4**: Evidence-First Claim Chart Engine with Substring Quote Verification.
- **Phase 5**: Professional REST APIs (Projects, Searches, Documents, Evidence, Exports, Evaluations).
- **Phase 6**: Scientific Evaluation Suite with Real Ground-Truth Benchmark Sets & Ablation Runs.
- **Phase 7**: Enterprise Frontend Application (Workspaces, Claim Chart Matrix, Document Viewer, Export Dossier).
- **Phase 8**: Verification, Quality Gate, Testing, Security Audit & Production Documentation.
